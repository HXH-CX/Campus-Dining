## 图片体积上限：5MB/20MB 不一致 → 统一 10MB

发现的问题不是"没兜底"（`uploadImage` 早就拦了"压缩失败 + 超 5MB"），而是：
1. 三处魔法数字（后端 config/.env 的 5、前端 beforeUpload 的 20），改一处就失配；
2. 判断以 `!compressed` 为前提 → 压缩"成功"但体积仍超标时会漏到后端，变成一句笼统的 400。

改法：后端 `UPLOAD_MAX_MB=10`（config + .env + .env.example）；前端 `api/upload.ts` 导出 `UPLOAD_MAX_MB` / `UPLOAD_MAX_BYTES`，`CreatePostView` 与 `EditPostDialog` 的 `beforeUpload` 引用常量；拦截条件改成只看 `compress.file.size`，并按是否压缩过给不同文案（"压缩后还有 X MB" / "图片有 X MB"）。

为什么是 10 而不是 5：手机直拍原图 3-8MB，5MB 会把正常照片挡在门外；前端压缩后通常 <500KB，这个上限只为"压缩失败退回原图"留余量。

## 菜品口味标签（提交 c1cef77，方案一）

按 AGENTS 第 4 条先给方案再动手：**给 dishes 加一列 JSON，不建 tags/dish_tags 两表**。

- 迁移 `2f7c4a9d31b8`：`tags JSON NOT NULL DEFAULT ('[]')`，MySQL 8.0.13+ 的表达式默认值，已有行直接拿空数组，不用 UPDATE 补数据。
- 词表 `app/core/tags.py`：口味 4（辣/清淡/重口/甜）+ 形态 7（米饭/面食/粉/汤/饺子/烧烤/小吃）+ 时段 1（早饭），`MAX_TAGS_PER_DISH=4`。
- 接口：`GET /dishes?tag=`、`GET /dishes/tags`（静态路径，必须抢在 `/dishes/{id}` 前注册）。
- 前端：搜索页 chips（带 count、0 值灰掉、再点取消、同步 URL）、详情页标签可点直接搜同类、后台弹窗一排胶囊选择器。

**核心坑**：`Dish.tags.contains([tag])` 永远返回 0 条。MySQL `JSON_CONTAINS(target, candidate)` 里，`candidate='"辣"'` 才是"数组包含这个标量"，传 `["辣"]` 变成"包含这个子数组"。SQLAlchemy 的 `contains()` 会把 Python 值 `json.dumps()` 后传进去，所以**传标量不传列表**。第一次测接口 total=0 才发现。

另一个语义细节：`DishUpdate.tags` 是 `None`=不动、`[]`=清空，和 `image_url` 的"非 None 才改"不同，注释和 AGENTS 都标了。

验证：journey 162/162（+9：清单字段、筛选结果都带该标签、不含无关菜、与关键词交集、未知标签返回空、详情带标签）、smoke 74/74、e2e 37/37（+9：chips 数量、灰态、筛选后数量变少且写 URL、选中态、取消、详情标签、点标签跳转、后台选择器、编辑回显）。CDP 实测「辣」4 道、「清淡」5 道、「辣+鸡」2 道；甜/粉/烧烤 count=0 且 chips disabled；375px 换行不溢出。

数据：20 道菜全部有标签，三种标签（甜/粉/烧烤）无菜——正好证明灰态逻辑可用，没有为了好看去硬凑。
